# Central HMSM roll processing for WebHDP-Link

This component runs the HMSM Studio optical CLI through the centrally managed HPC-Link adapter. Applications receive the published four-parameter contract, upload a scan and retrieve MIDI, measured candidate-note evidence, previews and a checksummed ZIP. They do not receive SSH or scheduler credentials.

The publication `link-hmsm-roll-vis` accepts one PNG, JPEG, TIFF or WebP scan per run. Its client permits 512 MiB per file. `model_id` selects one of eleven available roll profiles; `roll_speed` is 0.2–30 feet/minute; `method` is robust/background/adaptive/otsu; `polarity` is dark/light. Batch applications submit one durable run per scan. Discs, barrels, custom models and learned classifiers are outside this publication.

The processor performs CPU optical extraction. Its live validation policy reuses the already retained 12-hour `vis` A5000 reservation, also used for photogrammetry. A GPU is not intrinsically required for scan extraction. Operators can publish a separate allocation policy for another deployment; do not silently change an existing published version.

## Operator installation

1. Install the selected HMSM checkout's exact `requirements.txt` into a dedicated Python 3.12 environment. Do not modify a shared runtime.
2. Call `prepare_installation(destination, hmsm_source=..., runtime_python=..., remote_component_root=...)` from `external_code.webhdp_link_hmsm.seed`. The destination must be new. This copies an explicit scientific-source allowlist, the licenses and model catalog; rejects excluded development metadata; pins every file; and generates `manifest.json`, `component.json` and `checksums.json`. Retain the returned trusted configuration privately.
3. Copy that minimal installation to the matching operator-managed HPC component directory. Verify all checksums and the exact file inventory. Never copy the application checkout, credentials or development session files.
4. In the intended WebHDP application context, call `seed(app.native_pipeline_service, **trusted_configuration)`, then `save_publication(publication)`. Register the integrating application with exact origins, callbacks, publication permissions and quotas using the Link admin API. Follow `docs/guides/webhdp_link_deployment.md` for a production rollout; these steps do not deploy anything automatically.

Changes to runner bytes, scientific source, dependencies or published bindings require a reviewed new component/pipeline version. The live `1.0.0` installation is immutable. Requests cannot change executable paths, source pins, environment variables, arbitrary CLI options or allocation settings.

## Result interpretation

The MIDI and seven-note validation fixture establish the optical pipeline and transport contract. A historical roll still requires review of carrier, orientation, timing, scan quality and interpretation. `piano-report.json` preserves source SHA-256, parameters, model digest, scientific source identity, software versions, candidate notes and limitations. Where generated by HMSM, sealed physical observations and interpretation decisions are included in the evidence ZIP. Private project paths, native web project state and original scan bytes are excluded.

The integration imports generated MIDI into Studio only on an explicit user action, labeled as generated output rather than an independent reference performance. It does not replace native project provenance or disguise a remote result as a local processing receipt.

Run the focused boundaries with `.venv/bin/python -m pytest tests/test_webhdp_link_hmsm.py`. Actual CLI and browser/Draco acceptance evidence is retained in the WebHDP-Link report alongside independent MIDI and allocation checks.
